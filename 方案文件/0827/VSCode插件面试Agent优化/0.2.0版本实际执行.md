## 1. 本版本结论

0.2.0 已新增 `pi` runtime 配置，并在 Python 侧实现 `PiAgentRuntime`。该 runtime 吸收 Pi 的事件流、上下文外置、工具生命周期钩子和 `prepare_next_turn` 结构，但不直接安装或嵌入 TypeScript 版 `@earendil-works/pi-agent-core`。

默认 runtime 继续保持 `native`。`pi` 当前是可选实验 runtime，适合后续继续做真实 benchmark 和默认切换评估。

## 3. 关键实现取舍

1. 没有直接安装 TypeScript 版 Pi 包，避免把现有 Python 工具、会话落盘和 VS Code 协议整体迁移。
2. `PiAgentRuntime` 对外仍实现现有 `run()` 接口，因此 Webview 和 stdio 协议没有新增强制字段。
3. 工具执行仍为串行，保证工具通知顺序和历史消息顺序稳定。
4. 工具错误内部标记为 `is_error=True`，但写回历史时继续使用当前文本 observation，保持 LLM 自恢复行为兼容。
5. 历史压缩从 loop 主体中挂到 `prepare_next_turn` 默认策略，仍复用现有 [history.py](../../../agent/history.py)。

## 8. Pi 源码一致性补强执行记录

### 8.1 调整原因

用户对比真实 benchmark 后指出，`pi` runtime 虽然使用的内置工具与 `native` 接近，但 Pi 的核心不是把所有逻辑继续塞进原生 `agent_loop`，而是把上下文变换、LLM 消息转换、工具执行和下一轮准备拆成可组合的环节。

因此本次补强目标不是追求表面指标，而是让本项目的 `PiAgentRuntime` 在结构上更接近 Pi 源码中的 `AgentLoopConfig` / `AgentLoopContext` 思路，并与原生 loop 明确解耦。

参考源码：

- [agent-loop.ts](https://raw.githubusercontent.com/earendil-works/pi/main/packages/agent/src/agent-loop.ts)
- [types.ts](https://raw.githubusercontent.com/earendil-works/pi/main/packages/agent/src/types.ts)
- [README.md](https://raw.githubusercontent.com/earendil-works/pi/main/packages/agent/README.md)

### 8.2 实际改动

| 文件 | 改动 |
|---|---|
| [pi_runtime.py](../../../agent/pi_runtime.py) | 将上下文变换、LLM 消息转换、下一轮准备、工具执行从主循环中拆出；新增 `PiToolExecutor`；新增 `transform_context`、`convert_to_llm`、`prepare_next_turn`、工具前后置钩子和 turn 停止钩子 |
| [test_pi_runtime.py](../../../agent/tests/test_pi_runtime.py) | 补充 Pi-style 解耦测试，覆盖 transform/convert 顺序、`prepare_next_turn` 时机、`new_messages` 范围和独立工具执行器 |
| [prompt_builder.py](../../../agent/prompt_builder.py) | 优化系统提示词，明确 VS Code 工作区是“面试项目源码根目录”，不是 Interview Agent 插件自身源码 |
| [test_prompt_builder.py](../../../agent/tests/test_prompt_builder.py) | 增加系统提示词语义断言，避免后续回退 |

### 8.3 关键实现细节

1. `transform_context` 只影响本次 LLM 请求窗口，默认复用现有 `compress_history` / `enforce_token_limit`，不直接裁剪 `.sessions` 中的持久历史。
2. `convert_to_llm` 独立负责把 transform 后的上下文转换为模型请求消息，后续可在这里接入 Pi 兼容的消息 adapter。
3. `prepare_next_turn` 只在工具 turn 结束并准备进入下一轮前执行，首轮不会提前执行。
4. `PiToolExecutor` 独立负责工具参数解析、before/after 钩子、工具事件和 tool result 消息写回。
5. `agent_end.messages` 改为仅返回当前 run 新增消息，避免把历史会话误当作本轮增量输出。

## 9. Pi 工具链行为 benchmark 补强执行记录

### 9.1 对照 Pi 源码后的不足

本次重点对照 Pi 源码中的工具链行为，而不是只看 `pi` runtime 是否能跑通：

1. Pi 在工具执行前会处理“模型输出被截断但仍返回 tool calls”的场景，避免执行不完整参数；当前实现之前只要有 `tool_calls` 就会执行。
2. Pi 的工具链边界里有更清晰的 prepare / execute / result message 阶段；当前实现已拆出 `PiToolExecutor`，但 benchmark 还不能判断工具链是否真的被触发。
3. 用户真实 benchmark 中出现多轮 `tools=[]`，说明原 benchmark 只统计耗时，不足以识别“模型未按要求读取项目也回答”的无效样本。

### 9.3 Benchmark 行为标准

新 benchmark 输出中：

1. `status` 表示 runtime 是否正常完成或报错。

## 10. 工具调用实现解耦执行记录

0.2.0 前几轮已经完成 `native` / `langchain` / `pi` runtime 的切换与 Pi-style loop 解耦，但工具注册仍固定在 `SessionStore.build_default_registry()` 中。这样 runtime 虽然解耦了，工具来源、启用策略和后续用户安装工具包仍没有独立边界。

本次按 0.2.0 任务清单继续补齐工具调用实现解耦：先不做插件市场和 MCP 动态安装，只把工具注册入口、启用配置和 benchmark 可观测字段打通。
