# Interview Agent 0.2.0 版本优化任务清单

计划日期：2026-09-01

## 1. 本版本结论

0.2.0 的核心目标是：**新增 `pi` runtime 配置，并在 Python 侧实现一个 pi-style Agent runtime，让当前项目先拥有事件流、上下文外置、工具生命周期钩子这几个底层框架能力。**

本版本不建议直接把 `@earendil-works/pi-agent-core` TypeScript 包硬接进现有 Python 子进程。原因是当前项目的 Agent 主链路在 Python 内：模型客户端、工具注册、会话落盘、历史压缩、runtime 指标都已经围绕 [main.py](../../../agent/main.py)、[session.py](../../../agent/session.py)、[agent_loop.py](../../../agent/agent_loop.py) 建好。如果 0.2.0 直接把 loop 移到 VS Code Extension Host，会同时触发工具重写、会话格式迁移和 Node/Python 双 runtime 协调，风险大于收益。

更合适的最小路径是：

1. 配置层新增 `pi`，让用户能选择 `interview.agentRuntime=pi`。
2. Python 侧新增 [pi_runtime.py](../../../agent/pi_runtime.py)，吸收 Pi 的 loop 结构：`AgentContext`、`AgentEvent`、`beforeToolCall`、`afterToolCall`、`prepareNextTurn`、`shouldStopAfterTurn`。
3. 对外仍实现现有 [runtime.py](../../../agent/runtime.py) 的 `AgentRuntime.run()`，保证 VS Code 协议、Webview、历史会话和测试主链路不被大改。
4. 默认 runtime 继续保持 `native`，待 0.2.0 验证通过后，再在后续版本考虑是否默认切到 `pi`。

## 2. 用户想法与现有逻辑冲突检查

用户期望：把 Pi 底层的 `agent_loop` 运用到 `interview-agent`，为后续 Agent 底层框架打基础。

当前冲突点：

| 冲突点 | 当前项目逻辑 | Pi 逻辑 | 风险 | 0.2.0 处理方式 |
|---|---|---|---|---|
| 语言运行时 | Agent loop 在 Python 子进程内 | Pi core 是 TypeScript 包 | 直接接入会形成 Node/Python 双 loop，工具和会话都要桥接 | 0.2.0 做 Python pi-style runtime，不直接安装 TS Pi 包 |
| 对外接口 | `run()` 返回字符串，靠 `on_delta/on_tool_call` 回调通知 UI | `EventStream<AgentEvent, AgentMessage[]>` | 直接替换会破坏 [agentClient.ts](../../../vscode-extension/src/agentClient.ts) 和 Webview 协议 | 内部事件流，外部映射回现有回调 |
| 历史管理 | loop 内部直接 `compress_history` 和 `enforce_token_limit` | 通过 `transformContext` / `prepareNextTurn` 注入 | 若一次性迁移会影响历史恢复和 token 控制 | 先把压缩挪到 `prepare_next_turn` 默认策略 |
| 工具错误 | 工具异常转文本 observation | Pi 工具错误带 `isError`，由 runtime 结构化反馈 | 改错格式会影响模型自恢复与测试断言 | 内部保留 `is_error`，写回 OpenAI tool message 时仍保持文本兼容 |
| 工具并发 | 当前工具串行执行，通知 start/end 成对 | Pi 默认支持 parallel | 并行会打乱 UI 展示顺序，且内置工具线程安全未验证 | 0.2.0 默认 sequential，只预留 per-tool execution mode 字段 |
| 取消机制 | `should_cancel()` 轮询 + `AgentCancelled` | 标准 `AbortSignal` | Python 没有原生 AbortSignal，直接照搬会变复杂 | 用当前 `should_cancel` 模拟 signal 边界，不引入新依赖 |

结论：用户意图成立，但 0.2.0 不应做“TS Pi 包直连”。本版本要做的是**把 Pi 的 loop 结构迁入项目现有 runtime 边界**，先形成可测、可回退、可继续演进的底座。

## 3. 本版本范围

### 3.1 必做

1. 新增 `interview.agentRuntime=pi` 配置项，并贯通 VS Code Settings、TS 协议、Python init 参数和 `SessionStore` runtime 选择。
2. 新增 Python 侧 `PiAgentRuntime`，实现现有 `AgentRuntime` 协议。
3. 定义最小 `AgentEvent` / `AgentContext` / `AgentToolResult` 内部结构，支撑事件流和工具生命周期。
4. 把历史压缩从 pi-style loop 主体中解耦为 `prepare_next_turn` 默认策略。
5. 为工具调用增加 `before_tool_call` / `after_tool_call` no-op 钩子和结构化错误结果。
6. 保持 `native`、`langchain`、`pi` 三个 runtime 可切换，Demo Mode 仍强制使用 `native/FakeLLM`。
7. 增加单测覆盖：配置贯通、pi runtime 基础回答、工具调用、工具错误、取消、最大步数、历史落盘、runtime 指标。
8. 更新 README 和 0.2.0 实际执行记录模板。

### 3.2 暂不做

1. 不把默认 runtime 从 `native` 切到 `pi`。
2. 不安装 `@earendil-works/pi-agent-core` 到 VS Code 扩展依赖。
3. 不把 Python 工具重写成 TypeScript 工具。
4. 不引入真实 MCP client/server。
5. 不实现工具并行执行；先保留串行。
6. 不引入远程 tracing、LangSmith 或 Pi telemetry。
7. 不迁移 `.sessions` 历史文件格式。

## 4. 设计边界

### 4.1 Runtime 配置值

`interview.agentRuntime` 扩展为：

| 值 | 含义 | 0.2.0 默认 |
|---|---|---|
| `native` | 当前内置 [AgentLoop](../../../agent/agent_loop.py) | 默认 |
| `langchain` | 0.1.11/0.1.12 已接入的 LangChain 可选 runtime | 可选 |
| `pi` | 新增 Python pi-style runtime | 可选 |

无效值继续回退到 `native`，避免历史设置或手写配置导致启动失败。

### 4.2 Pi-style runtime 的最小接口

新增 [pi_runtime.py](../../../agent/pi_runtime.py)，对外保持：

```python
class PiAgentRuntime:
    @property
    def runtime_name(self) -> str:
        return "pi"

    def run(
        self,
        user_text: str,
        on_tool_call: ToolCallCallback | None = None,
        on_response: ResponseCallback | None = None,
        on_delta: Any = None,
        should_cancel: CancelCallback | None = None,
    ) -> str:
        ...
```

内部采用 pi-style 数据结构：

| 结构 | 用途 | 说明 |
|---|---|---|
| `AgentContext` | 外置上下文 | 持有 `system_prompt`、`messages`、`tools` |
| `AgentEvent` | 内部事件 | `agent_start`、`turn_start`、`message_start`、`message_update`、`message_end`、`tool_execution_start`、`tool_execution_end`、`turn_end`、`agent_end` |
| `AgentToolResult` | 工具结果 | `content`、`is_error`、`terminate`、`details` |
| `AgentLoopConfig` | loop 配置 | `prepare_next_turn`、`before_tool_call`、`after_tool_call`、`should_stop_after_turn` |

### 4.3 与 Pi 原始实现的取舍

Pi 原始 `agentLoop` 的核心特点包括事件流、可配置工具执行模式、`beforeToolCall` / `afterToolCall`、`shouldStopAfterTurn`、`convertToLlm` 和上下文转换。0.2.0 只吸收当前项目马上需要的部分：

| Pi 能力 | 0.2.0 是否实现 | 原因 |
|---|---|---|
| 事件流 | 实现内部事件，外部仍映射为当前回调 | 便于后续 UI 和诊断扩展 |
| `AgentContext` 外置状态 | 实现 | 为后续 compaction / steering 打基础 |
| `prepareNextTurn` | 实现默认策略 | 承接当前历史压缩逻辑 |
| `beforeToolCall` / `afterToolCall` | 实现 no-op 钩子 | 为工具权限、参数修正、诊断留边界 |
| `shouldStopAfterTurn` | 实现默认策略 | 替代部分写死停止条件 |
| parallel tool execution | 暂不实现 | 当前工具和 UI 顺序未验证线程安全 |
| steering / follow-up queue | 暂不实现 | 面试场景暂时没有后台消息队列 |
| TS SDK 直连 | 暂不实现 | 会扩大跨语言桥接成本 |

### 5.9 任务九：Pi 源码一致性补强

基于 Pi `agent-loop.ts` 和 `types.ts` 的源码校验，当前 `PiAgentRuntime` 还需要补强解耦边界，避免只是把 native loop 换个类名。

| 任务 | 说明 | 相关文件 |
|---|---|---|
| 增加 `transform_context` | 对齐 Pi 的 `AgentMessage[] -> transformContext() -> convertToLlm() -> LLM` 流程；默认 transform 负责历史压缩和 token 上限 | [pi_runtime.py](../../../agent/pi_runtime.py)、[history.py](../../../agent/history.py) |
| 增加 `convert_to_llm` | 在 LLM 调用边界转换消息；当前默认直通 OpenAI 格式，后续可过滤 UI-only / diagnostic message | [pi_runtime.py](../../../agent/pi_runtime.py) |
| 修正 `prepare_next_turn` 时机 | 只在 `turn_end` 之后、下一轮开始前调用，不再每次 LLM 调用前混用为历史压缩 | [pi_runtime.py](../../../agent/pi_runtime.py) |
| 拆出工具执行器 | 将工具参数解析、before、execute、after、tool result message 写回拆出为独立 `PiToolExecutor` | [pi_runtime.py](../../../agent/pi_runtime.py) |
| 修正 `new_messages` | `turn_end` / `agent_end` 中的 `new_messages` 只包含本次 run 新产生的消息，不再传全量历史 | [pi_runtime.py](../../../agent/pi_runtime.py) |
| 补充一致性测试 | 覆盖 transform/convert 调用顺序、prepare 调用时机、工具执行器事件、`new_messages` 语义 | [test_pi_runtime.py](../../../agent/tests/test_pi_runtime.py) |

验收标准：

1. LLM 调用前的消息处理顺序明确为 `transform_context -> convert_to_llm -> LLMClient.chat`。
2. 历史压缩只作为默认 `transform_context`，不再写死在主循环里。
3. `prepare_next_turn` 能看到完整 turn context，并只在存在上一轮完成结果且需要继续时执行。
4. 工具执行逻辑可单独测试，runtime 主循环只负责 turn 编排和事件派发。
5. `new_messages` 不包含进入本次 run 前已经存在的历史消息。

### 5.10 任务十：Pi 工具链行为 benchmark 补强

基于 Pi 源码中 `executeToolCalls`、`failToolCallsFromTruncatedMessage`、`prepareToolCall` 和 `createToolResultMessage` 的行为对比，当前实现仍需要补齐工具链可验收能力。重点不是让 benchmark 更快，而是让它能识别“模型是否真的按任务使用了工具”。

| 任务 | 说明 | 相关文件 |
|---|---|---|
| 记录 LLM 停止原因 | 在 `LLMResponse` 中保留 OpenAI `finish_reason`，让 runtime 能区分正常工具调用与 `length` 截断 | [llm_client.py](../../../agent/llm_client.py) |
| 截断工具调用保护 | 当模型因 `length` 停止但返回 tool calls 时，不执行参数可能不完整的工具调用，改为生成错误 tool result 让模型重发 | [pi_runtime.py](../../../agent/pi_runtime.py) |
| 工具行为 benchmark 判定 | benchmark 提示词明确要求先读项目结构/代码；输出 `tool_call_count`、`required_tool_used`、`tool_sequence` 和 `benchmark_status` | [runtime_benchmark.py](../../../agent/runtime_benchmark.py) |
| 低工具调用标记 | 如果一轮 benchmark 未调用 `list_directory` / `search_code` / `read_file`，标记为 `insufficient_tool_use`，避免把“没读项目也回答”误判为有效样本 | [runtime_benchmark.py](../../../agent/runtime_benchmark.py) |
| 补充工具链测试 | 覆盖截断工具调用不执行、finish reason 解析、benchmark 工具行为指标和不足工具调用标记 | [test_pi_runtime.py](../../../agent/tests/test_pi_runtime.py)、[test_llm_client.py](../../../agent/tests/test_llm_client.py)、[test_runtime_benchmark.py](../../../agent/tests/test_runtime_benchmark.py) |

验收标准：

1. `finish_reason="length"` 且存在 tool calls 时，`pi` runtime 不执行真实工具，只写回错误 observation。
2. benchmark 输出能直接看出工具调用数量、工具顺序和是否满足“必须读取项目”的行为要求。
3. 未触发关键工具的轮次不再只显示 `status=done`，而是额外标记 `benchmark_status=insufficient_tool_use`。
4. 新增测试覆盖上述行为，且 Python 全量测试、Ruff、扩展单测、类型检查和打包通过。

### 5.11 任务十一：工具调用实现解耦

当前四个工具由 `SessionStore` 里的 `build_default_registry()` 直接硬编码注册，导致 runtime 选择已经解耦，但工具来源和用户启用策略仍未解耦。本任务在 0.2.0 内先完成工具注册边界调整，为后续用户安装工具包、MCP adapter 和权限控制打基础。

| 任务 | 说明 | 相关文件 |
|---|---|---|
| 新增工具 provider | 新增基础工具 provider，负责声明和创建内置工具；`SessionStore` 不再直接 import 具体工具类 | [registry.py](../../../agent/tools/registry.py)、[session.py](../../../agent/session.py) |
| 新增工具元信息 | 暴露 `name`、`provider`、`description`、`risk_level`、`enabled_by_default`，用于后续 UI 和权限策略 | [registry.py](../../../agent/tools/registry.py) |
| 支持启用工具列表 | Python `configure()` 支持 `enabled_tools`；未配置时使用默认基础工具；未知工具忽略，不让 runtime 崩溃 | [session.py](../../../agent/session.py)、[main.py](../../../agent/main.py) |
| VS Code 配置接入 | 新增 `interview.enabledTools`，通过 init 协议传给 Python | [package.json](../../../vscode-extension/package.json)、[extension.ts](../../../vscode-extension/src/extension.ts)、[agentClient.ts](../../../vscode-extension/src/agentClient.ts)、[protocol.ts](../../../vscode-extension/src/protocol.ts)、[webviewPanel.ts](../../../vscode-extension/src/webviewPanel.ts) |
| benchmark 输出工具配置 | benchmark 输出 `available_tools`、`enabled_tools`，便于确认 LLM 看到的工具 schema 是否符合配置 | [runtime_benchmark.py](../../../agent/runtime_benchmark.py) |
| 补充解耦测试 | 覆盖 provider 默认注册、按名称过滤、未知工具忽略、协议透传和 benchmark 工具配置输出 | [test_tool_registry.py](../../../agent/tests/test_tool_registry.py)、[test_session.py](../../../agent/tests/test_session.py)、[test_main.py](../../../agent/tests/test_main.py)、[protocol.test.ts](../../../vscode-extension/test/protocol.test.ts)、[agentClient.test.ts](../../../vscode-extension/test/agentClient.test.ts)、[manifest.test.ts](../../../vscode-extension/test/manifest.test.ts) |

验收标准：

1. 不配置 `enabled_tools` 时，默认四个基础工具仍可用。
2. 配置 `enabled_tools=["list_directory","search_code"]` 时，LLM 只能看到这两个工具 schema。
3. 配置未知工具名时忽略未知项，已有有效工具仍正常注册。
4. `native` / `pi` / `langchain` 都只依赖最终 `ToolRegistry`，不关心工具来源。
5. benchmark 能输出本轮 `available_tools` 和 `enabled_tools`。
6. Python 全量测试、Ruff、VS Code 单测、类型检查、编译和打包全部通过。

## 9. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| `pi` 名称让人误以为直接依赖官方 TS 包 | 用户理解偏差 | README 和执行记录写清是 Python pi-style runtime |
| 事件模型引入过度设计 | 代码膨胀、测试变复杂 | 事件只服务当前回调、诊断和未来扩展，不做完整外部事件 API |
| 工具错误格式变化 | LLM 自恢复变差 | 写回历史时继续保留当前文本 observation |
| 并行工具调用提前接入 | 工具顺序、UI 顺序和线程安全风险 | 0.2.0 强制 sequential |
| 历史压缩迁移时机变化 | token 控制与 native 不一致 | 用与 native 相同的测试样例对齐行为 |
| 真实模型 tool calling 差异 | `pi` runtime 假测通过但真实失败 | 保留真实手工验收，不切默认 |
| VSIX 包体积增长 | 发布包变大 | 不新增 npm 运行依赖，不安装 TS Pi 包 |

## 10. 本版本改进建议

1. 0.2.0 应聚焦 runtime 底座，不要顺手做多 Agent、MCP、远程 tracing 或 UI 大改。
2. `pi` runtime 先作为可选实验分支，跑通后再考虑默认切换。
3. 事件流先内部使用，避免过早承诺新的外部协议。
4. 工具并发不要在 0.2.0 做，等工具线程安全和 UI 顺序需求明确后再加。
5. 当前已有 `native` 足够稳定，新增 `pi` 的价值应该体现在结构可演进，而不是为了替换而替换。

## 11. 下一个版本的优化建议

1. 0.2.1 可增加 `pi` runtime 的真实 benchmark，对比 `native` / `langchain` 的首 token、总耗时、工具耗时和错误率。
2. 0.2.1 可评估是否把诊断面板从“最近一轮指标”扩展到“runtime 对比表”。
3. 如果 `pi` runtime 稳定，再考虑把默认 runtime 从 `native` 调整为 `pi`，但必须先有真实样本闸门。
4. 可以开始评估 `before_tool_call` 用于工具权限提示，例如读取大文件、访问隐藏目录前提示或限制。

## 12. 后续可扩展的优化建议

1. 后续接入 MCP 时，只需要把 MCP tool adapter 转成当前 `Tool` 协议，再进入 `pi` runtime 的工具生命周期。
2. 如果出现多面试官、评分员、总结员协作需求，再基于 `AgentEvent` 和 `AgentContext` 扩展多角色编排。
3. 若未来确实需要官方 Pi TypeScript SDK，可先做独立 PoC：在 Extension Host 内跑 Pi，Python 子进程只保留工具服务；通过指标证明收益后再迁移。
4. 可以把 `prepare_next_turn` 扩展为可插拔 compaction 策略，例如摘要、最近窗口、按工具结果重要性保留。
5. 可以把 `AgentEvent` 进一步用于导出诊断报告，但默认仍不能包含 API Key、完整简历正文或完整代码文件内容。
