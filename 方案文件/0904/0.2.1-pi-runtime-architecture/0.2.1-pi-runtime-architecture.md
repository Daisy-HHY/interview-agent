**版本：** 0.2.1

## 3. 当前实现基线

当前代码已经具备 Pi-style 的雏形，但存在“接口已定义、生产装配未接通”的问题：

|---|---|---|

## 4. 设计原则与边界

### 4.1 本版本坚持的原则

1. **复用现有 runtime 外部协议。** `AgentRuntime.run()`、`messages`、`runtime_name` 和现有回调继续兼容 native/langchain。
2. **Pi 只提供内部组织方式。** 借鉴上下文、事件、工具生命周期和会话状态的组织思想，不复制 Pi 的 CLI、TUI、扩展生态或 TypeScript agent loop。
3. **先稳定内部事件，再暴露协议。** 事件模型和协议通知之间增加适配边界，避免把内部 Python 对象直接泄漏给 TS。
4. **持久化格式向后兼容。** 0.2.1 继续读写现有 JSON 消息数组，不在本版本引入 session tree 或新的强制迁移格式。
5. **安全优先加载 hook。** 不直接无条件执行工作区中的任意 Python 文件。0.2.1 先完成运行时内部 hook 注册面；外部 hook 文件加载要经过显式配置、路径约束和错误隔离后再决定是否落地。
6. **可验证优先。** 每个任务都要有最小失败测试、回归测试和明确验收标准。

### 4.2 本版本不做

- 不把 `native` 默认值切换为 `pi`。
- 不引入官方 Pi TypeScript 包，不改造成 Pi SDK。
- 不实现 MCP client adapter。
- 不实现 session tree、fork、navigate、steer 或 follow-up 控制流。
- 不实现依赖额外 LLM 调用的智能摘要压缩；本版本只稳定上下文转换扩展点和确定性裁剪边界。
- 不优先建设完整 Webview 事件时间线 UI；先完成协议和最小解析测试，UI 放到后续版本。
- 不借机重构 native/langchain 的正常逻辑。

## 6. 详细任务

### PI-01 固化 Pi-style runtime 内部架构契约

**目标：** 先定义“采用 Pi 思想”的范围，防止实现过程重新长成一个复制版 `agent_loop`。

**计划内容：**

- 以 [runtime.py](../../../agent/runtime.py) 的 `AgentRuntime` 为外部稳定边界。
- 在 [pi_runtime.py](../../../agent/pi_runtime.py) 中明确以下职责：
  - `AgentContext`：当前 system prompt、消息历史和工具注册表；
  - turn 生命周期：一轮用户输入、模型响应、工具执行和结束状态；
  - `PiToolExecutor`：工具解析、审批/拦截、执行、错误观察和工具结果消息；
  - context pipeline：生成 LLM 请求前的上下文转换；
  - event sink：把内部事件交给外部适配器；
  - session adapter：由外部会话仓库负责恢复和保存，不让 runtime 直接依赖文件系统。
- 记录哪些能力是 Pi-style 借鉴，哪些能力明确不兼容或不实现。
- 不新增与当前需求无关的抽象层；如果现有方法已经满足边界，只补协议说明和测试，不机械改名。

**验收标准：**

- 能用一页文档说明一次 `run()` 的状态流转和各组件职责。
- `native`、`langchain`、`pi` 仍共用现有 `AgentRuntime` 外部接口。
- 不出现第二套通用 agent loop；Pi runtime 的循环逻辑仍只服务当前项目。
- 先补充至少一个针对职责边界的失败测试，再进入后续实现。

### PI-02 接通 SessionStore 的 runtime 装配与 hook 注册

**目标：** 解决当前 hook 只在单测生效、生产构造没有传入 `AgentLoopConfig` 和 `event_sink` 的问题。

**计划内容：**

- 在 [session.py](../../../agent/session.py) 的 runtime 构造路径中建立 Pi 专用装配函数，集中创建 `AgentLoopConfig` 和事件适配器。
- 保证 `PiAgentRuntime` 的 `transform_context`、`convert_to_llm`、`prepare_next_turn`、`before_tool_call`、`after_tool_call` 和 `should_stop_after_turn` 可以从装配层注入。
- 默认未注册 hook 时继续使用 no-op/default 行为。
- 0.2.1 优先支持进程内、显式注册的 hook；不要直接执行工作区固定文件 `interview_pi_hooks.py`。
- 如后续确实需要外部 hook 文件，另立安全设计：显式路径配置、workspace 边界校验、导入异常隔离、API 版本校验和敏感数据约束，放入 0.2.2 决策项。

**验收标准：**

- 通过 `SessionStore` 创建的 Pi runtime 能触发至少一个 before/after hook 和一个 context hook。
- hook 抛出异常时有明确错误边界，不破坏 native runtime 和其他 session。
- 未启用 hook 时现有 Pi 单测和会话行为不变。
- 不把 API Key、完整工具结果或完整上下文通过 hook 日志输出。

### PI-03 建立统一的上下文处理管线

**目标：** 把 Pi 的“上下文是可变换的外置状态”落实为项目自己的可测试管线，为后续 compaction 留出边界。

**计划内容：**

- 固化调用顺序：`context snapshot → transform_context → convert_to_llm → LLMClient.chat`。
- 明确 transform 只影响本次模型请求，不能无意修改持久化历史；如果确实要更新历史，必须通过明确的 context/session 更新接口。
- 保留现有 `compress_history` 和 `enforce_token_limit`，先完善取消检查、system 消息保留、tool message 合法性和消息顺序测试。
- 为后续摘要压缩保留扩展点，但 0.2.1 不增加额外摘要模型调用、不改变历史文件格式。

**验收标准：**

- 有测试证明转换顺序严格为 `transform_context → convert_to_llm → chat`。
- 转换失败、取消和非法消息都能得到稳定结果，不产生半截工具调用历史。
- system prompt、当前用户问题和合法 tool result 的保留规则可被测试验证。
- 不改变 native runtime 当前的历史压缩行为。

### PI-04 建立内部事件到协议的适配层

**目标：** 让 Pi 事件流具备可观测出口，但控制事件量和敏感信息范围。

**计划内容：**

- 在 [protocol.py](../../../agent/protocol.py) 增加 `agent_event` 通知封装；在 [protocol.ts](../../../vscode-extension/src/protocol.ts) 增加对应类型和解析分支。
- 0.2.1 只透出关键事件：`agent_start`、`agent_end`、`turn_start`、`turn_end`、`tool_execution_start`、`tool_execution_end`、必要的 `message_update`。
- 事件统一带 session 标识、事件类型和可选时间信息；工具事件只传工具名、参数键名、耗时、结果长度和错误分类，不传完整结果。
- 由适配层过滤内部对象，禁止把 `AgentContext`、完整消息历史和 `AgentToolResult.details` 原样序列化。
- Webview 只做兼容解析和最小隐藏式记录；完整可视化时间线不列入本版本交付。

**验收标准：**

- Python 协议测试能验证事件序列化、UTF-8、空字段和脏数据容错。
- TS 协议测试能解析 `agent_event`，未知事件字段不导致 Extension Host 崩溃。
- 事件通知不会改变现有 `stream/tool_call/done/error` 时序。
- 输出中不包含 API Key、完整 prompt、完整工具结果或敏感文件内容。

### PI-05 Demo Mode 真正运行 Pi runtime

**目标：** 在不调用真实模型的前提下验证 Pi runtime，而不是设置选择 Pi、实际却运行 native。

**计划内容：**

- 修改 [session.py](../../../agent/session.py) 的 runtime 选择策略：Demo Mode 禁止误调真实的 LangChain 路径，但允许 `agent_runtime=pi` 使用 `_build_demo_llm()`。
- [main.py](../../../agent/main.py) 的 `runtime_metric` 继续记录实际 runtime；前端配置摘要不要在 Demo 下硬编码成 native。
- 增加 Pi Demo 的跨层测试：`init(agent_runtime=pi) → chat → tool/stream → runtime_metric → done → save`。
- 保持 `agent_runtime=native` 的 Demo 行为和兼容性不变。

**验收标准：**

- `INTERVIEW_FAKE_LLM=1` 且 `agent_runtime=pi` 时，实际实例类型为 `PiAgentRuntime`，不是 `AgentLoop`。
- 不配置真实 API Key 也能完成至少一轮 Pi 文本回答和一轮工具调用场景。
- `runtime_metric.runtime` 与实际运行实例一致，UI 不再显示误导性的 `native（Demo）`。
- Demo Mode 不会因为 Pi 配置而触发真实网络请求。

### PI-06 解耦 SessionStore 与 runtime 私有历史字段

**目标：** 保持现有 `.sessions/{id}.json` 兼容，同时消除 `_restore()` 直接写 `loop._messages` 的实现耦合。

**计划内容：**

- 在 [runtime.py](../../../agent/runtime.py) 为历史恢复补充最小公开能力，或采用等价的 runtime-specific adapter；不得把文件读写职责放入 `PiAgentRuntime`。
- 在 [session.py](../../../agent/session.py) 统一处理新建 runtime、读取 JSON、校验 system 消息、恢复消息和保存消息。
- 对 native、langchain、pi 分别验证恢复行为；损坏 JSON、旧格式、孤立 surrogate 和非法 tool message 继续按现有容错策略处理。
- 不在本版本把线性数组迁移为 JSONL 或树状 session 文件。

**验收标准：**

- `_restore()` 不再依赖 Pi runtime 的私有 `_messages` 属性。
- 现有历史文件可以继续恢复，保存后的字段和角色顺序兼容 0.2.0。
- Pi runtime 恢复后继续对话，context 和事件流均正常。
- 损坏历史不会导致进程崩溃，也不会越界写出 `.sessions` 目录。

### PI-07 增加 FakeLLM benchmark 与 Pi 回归场景

**目标：** 建立低成本、可重复的 Pi 底层行为回归，不急于用不一致的真实模型数据决定默认 runtime。

**计划内容：**

- 在 [runtime_benchmark.py](../../../agent/runtime_benchmark.py) 增加 `--fake-llm` 或等价模式；FakeLLM 模式不要求 `INTERVIEW_API_KEY`。
- 保留真实 benchmark 的 API Key 环境变量读取方式，不把密钥写入命令参数、日志或 JSONL。
- 增加固定场景：纯文本回答、单工具调用、连续多工具调用、工具失败、取消、达到最大步数、历史恢复、Demo Pi。
- `--runtime pi` 可独立执行；`--runtime all` 明确包含 Pi。是否修改默认 benchmark runtime 另行评估，不影响产品默认 runtime。
- 指标至少包含：status、configured/runtime、首 delta、模型耗时、总耗时、工具序列、工具调用成功/失败、估算 token 数；不保存完整 prompt 和工具结果。

**验收标准：**

- 无 `INTERVIEW_API_KEY` 时，FakeLLM benchmark 可以成功运行并输出 JSONL。
- 同一场景重复运行，工具顺序、结束状态和历史角色结果稳定。
- benchmark 能区分“完成但未使用必需工具”和真正成功，避免只看 status。
- 现有 `test_runtime_benchmark.py` 和新增 Pi 场景测试全部通过。

### PI-08 补齐架构文档、验收和发布闸门

**目标：** 让后续开发者知道当前项目的 Pi runtime 是什么、不是“官方 Pi SDK”，以及如何验证。

**计划内容：**

- 增加 Pi 能力对照表：事件流、工具 hook、context pipeline、compaction 扩展点、会话持久化、session tree；标记“本项目已实现/仅借鉴/后续规划”。
- 记录本版本不切默认、不引入 MCP、不做 session tree 和智能摘要的原因。
- 为 0.2.1 生成实际执行记录时，单独记录测试命令、失败复现、修复结果和未覆盖风险；不要把预置计划冒充实际执行过程。

**验收标准：**

- README 的配置、runtime 名称和 Demo 行为与代码一致。
- 新开发者无需阅读 Pi 源码即可理解项目 runtime 边界。
- 版本验收记录列出所有测试、类型检查、lint 和编译结果。

  ```powershell
  cd vscode-extension
  npm test
  npx tsc -p ./ --noEmit
  ```

## 9. 0.2.1 完成定义（Definition of Done）

只有同时满足以下条件，才可以将版本标记为完成：

1. Pi runtime 的 context、turn、tool executor、event sink 和 session adapter 职责已经文档化。
2. Pi 的 hooks 和 event sink 已从 SessionStore 生产装配路径接通。
3. Demo Mode 可以真实运行 Pi + FakeLLM，且指标反映实际 runtime。
4. 事件协议完成 Python/TS 双侧类型与容错测试，且不泄漏敏感内容。
5. 历史恢复不依赖 runtime 私有字段，0.2.0 JSON 历史兼容。
6. FakeLLM benchmark 可在无 API Key 条件下运行，固定 Pi 场景稳定通过。
7. `pytest`、`ruff`、`npm test`、TypeScript 检查和扩展编译均通过；失败项必须记录原因，不得用跳过测试代替修复。
8. 默认 runtime 仍为 native，后续是否切换由独立 benchmark 数据和产品决策决定。

## 10. 版本任务清单本身的改进建议

- 任务拆分已经把“底层架构接通”和“产品体验扩展”分开，建议实施时每个 PI 任务保持一个可回滚的小变更单元。
- hook 外部文件加载涉及执行任意 Python 代码，建议在真正实现前补一轮安全评审，不要把“固定文件自动导入”直接当成默认方案。
- benchmark 先采用 FakeLLM 做行为闸门，真实模型 benchmark 只作为性能补充；不同模型、Prompt 和工具策略必须分组记录，不能混算。
- `agent_event` 先传关键事件，等事件字段稳定后再扩展 UI，避免先做展示再反复改协议。

## 11. 下一个版本的优化建议（0.2.2）

- 基于 0.2.1 稳定的 context pipeline 实现 checkpoint 式摘要压缩，先支持可选、可关闭和失败回退。
- 增加轻量 Webview runtime 事件时间线，展示 turn、工具耗时、首 token 和错误分类。
- 评估显式 `piHooksFile` 配置和安全加载机制，决定是否开放给高级用户。
- 建立最小 CI workflow，在 FakeLLM 模式下运行全部 runtime 回归并保存脱敏指标。
- 在工具 registry 边界上设计 MCP adapter，但先完成接口设计和隔离测试，不直接扩大本版本范围。

## 12. 后续可扩展的优化建议

- 会话从线性 JSON 演进为可分支的 session tree，同时保留旧会话读取能力。
- 增加 steer、follow-up 等交互控制语义，但要先明确协议时序和并发模型。
- 引入 trace id、结构化 stderr 日志和跨 session 诊断查询。
- 支持多工具 provider 和远程工具的统一生命周期、超时、取消和权限控制。
- 当 Pi 在行为正确性、工具成功率和可观测性上连续满足门槛后，再讨论是否将默认 runtime 从 native 切换为 pi。
