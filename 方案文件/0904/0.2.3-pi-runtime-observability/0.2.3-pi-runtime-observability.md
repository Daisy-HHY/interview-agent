# 0.2.3 Pi Runtime 可观测性与自适应预算优化任务清单

**版本：** 0.2.3  
**主题：** 时间线最小视图、压缩质量评估、诊断记录边界与动态安全阀  
**状态：** 已实施并完成自动化回归；真实模型质量评测需配置 API Key 后按验收文档执行  
**前置版本：** 0.2.2 Pi runtime extension

执行记录： [0.2.3-pi-runtime-observability-实际执行.md](0.2.3-pi-runtime-observability-实际执行.md)  
验收文档： [0.2.3-pi-runtime-observability-验收步骤以及验收标准.md](0.2.3-pi-runtime-observability-验收步骤以及验收标准.md)

## 1. 版本目标

在 0.2.2 已具备的 checkpoint 压缩、脱敏 `agent_event`、内存时间线和可配置运行预算基础上，先建立可验证的数据和边界，再决定是否增加更重的能力：

1. 将 runtime 时间线稳定为低噪声、脱敏、有容量上限的调试视图。
2. 用真实模型数据评估确定性压缩是否值得升级为可选 LLM summarizer。
3. 在扩展为 trace/诊断记录前，完成隐私、保留周期和存储上限设计。
4. 根据运行预算的真实命中率，设计可解释的动态安全阀，不直接取消安全上限。

本版本继续采用 Pi 的设计思想，不照搬官方 Pi 的 `agent_loop`，不引入官方 Pi SDK，也不改变默认 `native` runtime。

## 2. 第 1 项的含义说明：为什么先做调试型最小时间线

### 2.1 “时间线”是什么

这里的时间线不是聊天正文，也不是完整的工具结果面板，而是把 runtime 发出的关键事件按顺序列出来，用于回答：

- 当前运行到了哪个阶段；
- 执行了哪个工具；
- 哪一步耗时较长；
- 是否发生错误、取消或上下文压缩；
- 模型为什么继续运行或结束。

0.2.2 已经有这类能力的初版：Webview 在内存中接收脱敏 `agent_event`，聚合连续 `message_update`，按事件序号排序，并限制最大事件条数。

### 2.2 “调试型最小视图”是什么

只展示定位问题所必需的信息，例如事件类型、序号、相对耗时、turn/step、工具名、状态、结果长度和错误分类；不展示完整 prompt、模型思考正文、工具参数值、工具结果正文或完整上下文。

它的重点是“可判断运行状态”，不是“还原全部执行细节”。这样可以控制隐私风险、前端内存和渲染噪声，也能避免 UI 在协议尚未稳定时过早绑定复杂交互。

### 2.3 “稳定事件字段”是什么

在继续增加筛选、持久化和图形化之前，先确定事件合同：

- 事件名称、生命周期和顺序含义；
- 必填字段、可选字段、字段类型和默认值；
- `event_seq`、耗时和 turn/step 的定义；
- 重复、乱序、缺字段和未知事件的处理方式；
- 脱敏边界和向后兼容方式。

字段一旦稳定，后续筛选、查询、导出和可视化都可以依赖同一份数据，不需要为每种 UI 重新猜测事件含义。

### 2.4 “容量上限”是什么

同时限制两类资源：

- 事件数量上限：长时间运行时只保留最近的有限事件；
- 单事件和聚合文本上限：不因异常长的错误、工具输出或流式事件占满 Webview 内存。

达到上限时应丢弃最旧的调试事件或截断展示文本，并明确记录丢弃/截断计数；不能让时间线无限增长。

### 2.5 “再考虑筛选、持久化和可视化增强”的含义

这是分阶段策略：

```text
稳定事件合同与容量边界
        ↓
验证时间线不会泄露、失控或拖慢正常回答
        ↓
再增加筛选/搜索
        ↓
再决定是否持久化为 trace/诊断记录
        ↓
最后根据实际使用场景增加图表和复杂交互
```

如果第一阶段的数据结构、隐私边界或容量控制尚不稳定，直接增加持久化和可视化会把临时字段固化，后续迁移成本和泄露风险都会变高。

## 3. 范围与非目标

### 3.1 本版本范围

- 稳定最小 runtime 事件合同并补齐兼容测试。
- 固化时间线事件数量、文本大小和内存行为上限。
- 建立真实模型压缩评测数据格式、采集流程和判断门槛。
- 完成是否引入可选 LLM summarizer 的决策，不以“必须接入”为目标。
- 完成 trace/诊断记录的隐私与存储设计评审，不默认落盘。
- 用历史运行数据评估固定预算命中率，提出动态安全阀的最小策略。

### 3.2 本版本明确不做

- 不默认引入 LLM summarizer。
- 不把完整 prompt、工具参数、工具结果或模型思考正文写入时间线或诊断记录。
- 不默认持久化 runtime trace，不新增数据库或外部观测服务。
- 不实现复杂筛选器、搜索页、瀑布图、统计图或跨会话分析界面。
- 不取消最大步数、超时、取消和异常保护。
- 不把动态预算做成不可解释的黑盒模型。

## 5. 详细任务

### PI23-01 固化最小 runtime 事件合同

**目标：** 让后端事件、TypeScript 类型和 Webview 展示依赖同一份稳定语义。

**计划内容：**

- 以现有 [`protocol.py`](../../../agent/protocol.py)、[`pi_runtime.py`](../../../agent/pi_runtime.py) 和 [`protocol.ts`](../../../vscode-extension/src/protocol.ts) 为基础，整理事件字段清单。
- 固定最小字段：事件类型、事件序号、相对耗时；按事件类型保留 turn/step、工具名、状态、长度和错误分类等可选字段。
- 明确 `agent_start`、`turn_start`、`tool_execution_start`、`tool_execution_end`、`message_update`、`context_compaction`、`turn_end`、`agent_end` 的顺序和语义。
- 增加协议版本字段或等价的兼容约定；未知字段允许忽略，未知事件不能阻塞正常回答。
- 统一数值单位、空值处理、事件序号单调性和服务端/客户端时间的边界。
- 继续禁止完整 prompt、摘要正文、工具参数值和工具结果进入普通事件。

**验收标准：**

- Python 协议测试和 TypeScript 类型/行为测试使用同一份字段约定。
- 缺少可选字段、增加未知字段、收到未知事件时，Webview 不报错且正常完成回答。
- 事件序号、耗时、turn/step 的含义有文档和测试覆盖。
- 脱敏测试确认敏感正文不会从 runtime 事件流出。

### PI23-02 完善时间线容量与异常边界

**目标：** 把 0.2.2 的“有限长度时间线”变成明确、可回归的资源边界。

**计划内容：**

- 复用现有 Webview 内存时间线和连续 `message_update` 聚合逻辑，不引入独立状态管理依赖。
- 明确最大事件数、单事件文本长度、聚合事件长度和丢弃计数；具体数值以当前 UI 性能和测试结果为依据固化。
- 事件超限时只保留最近事件，保留必要的开始/结束/错误状态，避免截断后无法判断本轮结果。
- 对重复、乱序、缺字段、空事件和极长错误信息做确定性处理。
- 新会话、完成、错误、取消和重新初始化时明确时间线重置或保留边界。

**验收标准：**

- 连续高频事件不会导致 Webview 事件数组和 DOM 无限增长。
- 在上限场景下，内存时间线、渲染耗时和最大文本量均不超过规定阈值。
- 超限后仍能看到当前运行状态和最终 done/error/cancelled 结果。
- 丢弃或截断行为可通过测试或调试计数确认，不影响普通消息和工具卡片。

### PI23-03 保持调试型最小视图

**目标：** 在事件合同稳定前控制 UI 复杂度，只优化可读性和排错效率。

**计划内容：**

- 保留现有时间线和小思考轨迹折叠能力，统一展示事件序号、耗时、事件类型、工具名、状态和错误分类。
- 不在本版本增加筛选、搜索、跨会话查询、导出、图表和详细 trace 页面。
- 对时间线不可用、未知事件或字段异常采用静默降级，不能阻塞流式输出、工具调用、done/error 状态。
- 只补充必要的“已截断/已丢弃数量”提示，避免把诊断区变成第二个聊天窗口。

**验收标准：**

- 文本、单工具、连续工具、工具失败、取消、压缩和超限场景均能看到最小调试信息。
- UI 不显示完整 prompt、思考正文、参数值和工具结果正文。
- 时间线异常不会改变现有输出、工具卡片和完成状态的时序。

### PI23-04 建立真实模型压缩评测集与指标

**目标：** 用真实模型数据判断当前确定性压缩是否已经够用，而不是凭主观感受直接引入摘要模型。

**计划内容：**

- 定义脱敏评测样本：纯对话、长任务、多轮工具调用、工具失败后恢复、上下文接近上限、压缩后继续执行。
- 为同一模型、同一 prompt、同一工具条件建立未压缩基线和确定性压缩对照组。
- 记录输入/输出 token、压缩前后 token、token 节省比例、压缩耗时、端到端延迟、失败/回退次数和任务完成率。
- 设计摘要质量检查：关键信息保留、当前任务可继续性、工具链完整性、事实一致性和最终任务结果。
- 真实数据只保存脱敏指标和样本编号；禁止把 API Key、完整 prompt 和工具结果写入报告。
- 区分 FakeLLM 的确定性回归结果和真实模型的质量/成本结果。

**验收标准：**

- 每个评测样本都能得到未压缩、确定性压缩两组可比结果。
- 报告至少包含质量、token 节省、压缩延迟、端到端延迟和失败率。
- 评测结果可重复运行，并能识别模型、配置和样本版本。
- 没有把 FakeLLM 结果误当作真实摘要质量结论。

### PI23-05 评估可选 LLM summarizer

**目标：** 只在真实数据证明收益足够时，决定是否设计可选摘要模型调用。

**决策门槛：**

- 语义质量明显优于确定性压缩，且关键任务信息保留稳定。
- token 节省收益能够覆盖摘要调用的额外 token 成本。
- 额外延迟在可接受范围内，不能显著拖慢普通回答。
- 摘要调用失败、超时、取消、格式错误时均能回退到确定性压缩或原上下文。
- 真实模型调用不会扩大敏感数据暴露面，配置和日志边界可说明。

**如果未达到门槛：** 保持确定性压缩，不添加 summarizer 依赖和配置。

**如果达到门槛：** 仅提出后续最小实现：显式开关、模型/预算配置、结构化摘要校验、超时取消、失败回退、脱敏事件和独立质量回归；本任务本身不默认接入。

### PI23-06 评估 trace/诊断记录边界

**目标：** 在任何持久化之前先回答“记录什么、保存多久、保存在哪里、谁能看到、达到多大停止”。

**计划内容：**

- 对比三种方案：仅内存时间线、会话内临时诊断记录、受控本地 trace 文件；不直接引入数据库或远程平台。
- 定义允许记录的字段、禁止记录的字段、脱敏规则和访问边界。
- 定义单会话最大记录量、全局存储上限、保留周期、清理触发时机和异常写入处理。
- 评估用户主动导出和自动落盘的差异；默认不改变现有隐私策略。
- 评估旧 session JSON 兼容性，避免把临时诊断字段写入业务会话历史。

**决策输出：**

- `keep-in-memory`：继续仅保留调试时间线；
- `session-diagnostic`：仅在用户显式开启时保存短期诊断记录；
- `trace-storage`：在隐私和存储评审通过后，进入后续版本实现。

**验收标准：**

- 形成字段白名单/黑名单、保留周期、容量上限和清理策略。
- 未完成评审前，不新增默认持久化路径。
- 记录方案不会写入完整 prompt、工具参数、工具结果、API Key 或模型思考正文。

### PI23-07 统计运行预算实际命中率

**目标：** 用实际运行数据识别固定 `piMaxSteps` 是过小、合理还是过大。

**计划内容：**

- 按文本回答、单工具、连续工具、工具失败恢复、压缩触发和取消场景统计实际 step 数。
- 记录达到安全阀的次数、自然结束次数、工具循环次数、单步耗时、累计耗时和上下文压力等级。
- 区分“达到预算后仍有未完成任务”和“达到预算时本来就应结束”，避免只看命中率做错误结论。
- 评估不同模型、工具集和工作区规模下的分布，不用单一平均值替代长尾数据。
- 使用脱敏聚合指标，不保存任务正文。

**验收标准：**

- 能计算安全阀命中率、自然结束率、工具循环分布、耗时分布和上下文压力分布。
- 能定位预算过小导致的提前结束，以及预算过大导致的无效循环。
- 统计不会改变现有 runtime 的执行路径和安全阀行为。

### PI23-08 设计动态安全阀最小策略

**目标：** 在保留硬上限的前提下，根据已观测信号调整软预算，减少提前停止和无效循环。

**建议策略：**

- 保留一个不可突破的全局硬上限。
- 以当前 step 作为基础预算，结合工具循环次数、单步/累计耗时和上下文压力计算是否允许继续。
- 工具连续成功且上下文压力低时，可在软预算内小幅延长；工具重复失败、循环无进展、耗时过长或上下文压力高时，提前进入收束/回退路径。
- 每次调整都发出脱敏原因和预算状态，保证可解释和可诊断。
- 初版优先使用确定性阈值，不引入训练模型或复杂策略引擎。
- 保留显式 `piMaxSteps` 配置，并保证配置值仍是最终硬边界之一。

**验收标准：**

- 动态策略不会绕过取消、超时、最大步数和错误保护。
- 对同一输入和同一事件序列，预算决策可重复。
- 预算调整原因可以从最小事件或诊断指标中解释。
- 通过对照测试确认：不会降低正常任务完成率，也不会放大无限工具循环风险。

### PI23-09 回归测试、文档与验收

**目标：** 把 0.2.3 的结论沉淀为可重复的开发和验收基线。

**计划内容：**

- 补充 Python 协议、压缩指标、预算统计和动态安全阀测试。
- 补充 Webview 时间线容量、乱序/重复/未知事件、截断和重置测试。
- 运行现有 Python 测试、ruff、扩展测试、TypeScript 检查、扩展 compile 和 FakeLLM benchmark。
- 真实模型评测单独记录模型、配置、样本版本、时间和脱敏结果，不作为无密钥 CI 的硬依赖。
- 在版本执行记录中记录实际采用的决策：是否引入 summarizer、是否持久化 trace、是否启用动态预算。
- 如果本轮代码修改后需要重新打包，按既有规则只重新打包一次。

## 7. 0.2.3 验收标准

1. 时间线事件字段、顺序、兼容和脱敏边界有文档与测试。
2. 时间线有明确的事件数、文本量和内存上限，超限后仍能显示最终状态。
3. 时间线保持调试型最小视图，不新增筛选、持久化和复杂可视化。
4. 真实模型压缩评测同时覆盖摘要质量、token 节省、延迟和失败率。
5. 是否引入 LLM summarizer 有数据依据；未达到门槛时保持确定性压缩。
6. trace/诊断记录在实现前明确字段隐私、保留周期、存储上限和默认策略。
7. 能根据真实数据计算安全阀命中率，并形成动态预算策略或明确暂缓理由。
8. 动态策略仍保留硬安全上限、取消、超时和失败回退。
9. 0.2.2 既有功能、历史 session 兼容、默认 native runtime 和现有 UI 时序不回归。

## 8. 本版本改进建议

- 将“评估”和“实现”拆开：PI23-05、PI23-06、PI23-08 首先交付决策材料，不因完成任务编号而强行接入新能力。
- 真实模型质量评估与 FakeLLM 回归分开；FakeLLM 只负责协议、边界和确定性行为。
- 对时间线只稳定一份最小事件合同，暂不为筛选、持久化和图表预留多套抽象。
- 所有新增指标优先使用聚合数值，避免为了观测而扩大敏感数据范围。

## 9. 下一个版本的优化建议

- 如果压缩质量和成本门槛通过，再实现显式开启的 LLM summarizer，并先支持单一模型、单一路径和确定性回退。
- 如果 trace 隐私和容量评审通过，再增加用户主动开启的短期本地诊断记录。
- 根据动态安全阀的线上/真实模型数据，继续校准工具循环、耗时和上下文压力阈值。
- 在事件合同连续稳定后，再增加最小事件级筛选和按会话的诊断导出。

## 10. 后续可扩展的优化建议

- 建立压缩质量评测集、工具选择质量评测集和成本回归基线。
- 在隐私治理成熟后，增加统一 trace id、跨 runtime 诊断和受控导出。
- 在确有使用需求且数据规模证明必要时，再增加事件筛选、搜索、瀑布图和统计可视化。
- 评估 session checkpoint/tree、分支回溯和压缩节点可见性，但不在本版本提前实现。
- 当正确性、工具成功率、成本、延迟和可观测性连续达到门槛后，再讨论默认 runtime 策略。
