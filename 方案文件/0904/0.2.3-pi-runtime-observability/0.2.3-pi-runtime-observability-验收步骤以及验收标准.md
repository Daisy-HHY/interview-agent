# 0.2.3 验收步骤以及验收标准

**适用范围：** Pi runtime 事件时间线、压缩评测、诊断记录边界和动态运行预算  
**验收原则：** 先完成自动化回归，再执行 Demo/UI 验收；真实模型质量不能用 FakeLLM 结果替代。

## 3. 压缩与指标验收

### 步骤 8：执行 FakeLLM 压缩对照

**操作：**

```powershell
cd D:\project\interview-agent
New-Item -ItemType Directory -Force -Path '.tmp\pi-runtime-023' | Out-Null
.\.venv\Scripts\python.exe -m agent.runtime_benchmark --workspace .tmp\pi-runtime-023 --runtime pi --rounds 1 --fake-llm --compaction-mode compare --compaction-trigger-tokens 100 --compaction-keep-messages 2 --compaction-seed-messages 12 --output .tmp\pi-runtime-023\compaction.jsonl --summary-output .tmp\pi-runtime-023\summary.json
Get-Content -LiteralPath '.tmp\pi-runtime-023\summary.json' -Encoding UTF8
```

**作用/目的：** 验证 benchmark 能产生同配置下的 baseline/compaction 对照，并且长上下文样本确实触发 0.2.2 的确定性压缩。

**通过标准：**

- baseline 和 compaction 均能完成；
- compaction 行的 `state` 为 `completed`；
- 存在 `before_tokens`、`after_tokens`、`compression_token_saved`、`compression_ratio` 和 `compression_elapsed_ms`；
- summary 能给出样本数、完成数、失败率、平均节省 token 和平均压缩耗时；
- `compression_quality_status` 为 `manual_review_required`，不把 FakeLLM 结果当成语义摘要质量。

### 步骤 9：执行真实模型 paired 评测（有 API Key 时）

**操作：** 在当前 shell 通过安全方式配置 `INTERVIEW_API_KEY`，不要把密钥写入命令参数、文件或报告；然后执行：

```powershell
.\.venv\Scripts\python.exe -m agent.runtime_benchmark --runtime pi --rounds 3 --compaction-mode compare --compaction-trigger-tokens 12000 --compaction-keep-messages 6 --compaction-seed-messages 12 --output .tmp\pi-runtime-023\real-compaction.jsonl --summary-output .tmp\pi-runtime-023\real-compaction-summary.json
```

**作用/目的：** 在同一模型、同一 prompt、同一工具和同一历史样本下比较未压缩与确定性压缩，得到真实 token、延迟和失败数据。

**通过标准：** 每个样本有 baseline/compaction 配对；报告至少包含：

- 摘要/上下文质量人工评分；
- 压缩前后 token 和节省比例；
- 压缩耗时和端到端延迟；
- 失败率、回退率和任务完成率。

当前环境未配置 `INTERVIEW_API_KEY` 时，此步骤标记为“外部条件未满足”，不得用 FakeLLM 结果代替。没有真实 paired 数据时，0.2.3 的合规决策是暂不引入 LLM summarizer。

### 步骤 10：人工检查压缩质量

**操作：** 对真实模型 paired 样本逐条检查：关键事实、当前任务、工具调用关系、失败恢复信息和最终任务结果；按“保留/部分保留/丢失”记录，不记录完整 prompt 或工具结果到公共报告。

**作用/目的：** `compression_token_saved` 只能说明 token 数变化，不能说明语义信息是否保留；本步骤负责补足自动指标不能判断的摘要质量。

**通过标准：** 压缩后仍能继续当前任务，合法 tool call/tool result 关系未被破坏，关键事实没有系统性丢失；若质量没有稳定优于确定性裁剪，保持不引入 LLM summarizer。

## 4. 时间线和隐私验收

### 步骤 11：检查事件合同和脱敏边界

**操作：**

```powershell
cd D:\project\interview-agent
rg -n 'schema_version|AGENT_EVENT_SCHEMA_VERSION|_safe_agent_event|完整 prompt|工具参数|工具结果' agent\protocol.py agent\tests\test_protocol.py vscode-extension\src\protocol.ts
```

**作用/目的：** 确认 Python 和 TypeScript 使用同一版本化事件合同，并确认事件只传聚合字段，不携带敏感正文。

**通过标准：** `agent_event` 包含 `schema_version=1`；未知事件被忽略；完整 prompt、参数值、工具结果和摘要正文不进入 `agent_event`。

### 步骤 12：执行 Demo/UI 时间线验收

**操作：**

1. 打开项目 `D:\project\interview-agent`，启动扩展开发宿主或安装当前本地扩展。
2. 打开任意测试工作区，启用 `interview.demoMode`，选择 `interview.agentRuntime=pi`。
3. 执行一次纯文本问题、一次单工具问题、一次连续工具问题和一次工具失败问题。
4. 打开诊断区域，观察 runtime、事件序号、耗时、step、工具、状态、长度、错误分类和预算信息。
5. 观察小思考轨迹：每组运行事件可折叠，展开后不显示完整 prompt、工具参数值或工具结果正文。

**作用/目的：** 验证最小时间线确实帮助调试，同时不把时间线变成第二个聊天窗口，也不影响原有 stream/tool/done/error 时序。

**通过标准：**

- 事件按 `event_seq` 有序显示；
- 连续 `message_update` 被聚合；
- 未知/缺字段事件不会导致 UI 报错；
- 时间线不阻塞回答、工具卡片或完成状态；
- 只显示调试摘要，不显示敏感正文。

### 步骤 13：检查容量上限

**操作：** 执行高频流式事件或超过 80 个 runtime 事件的长工具链场景；也可以直接运行 Webview 相关测试：

```powershell
cd D:\project\interview-agent\vscode-extension
npm test -- --run test/webview-template.test.ts
```

**作用/目的：** 验证长任务不会让 `runtimeEvents`、单行文本或时间线 DOM 无限增长。

**通过标准：**

- 最多保留 80 条事件；
- 单字段最多展示 160 个字符；
- 单行最多 320 个字符；
- 时间线总展示量最多 12,000 个字符；
- 超限后显示“已丢弃/已截断”计数；
- 最终 done/error/cancelled 或 `agent_end` 状态仍可判断。

### 步骤 14：确认 0.2.3 不默认持久化 trace

**操作：**

```powershell
rg -n 'localStorage|sessionStorage|runtimeEvents|runtimeTimeline|trace-storage|session-diagnostic' vscode-extension\src\webview\main.js agent README.md 方案文件\0904\0.2.3-pi-runtime-observability
```

**作用/目的：** 防止在事件字段尚未稳定时意外增加落盘、跨会话追踪或隐私泄露路径。

**通过标准：** 当前实现只有内存 `runtimeEvents`；没有 runtime trace 的默认文件、数据库、远程上报或浏览器持久化；业务 `.sessions` 文件格式不新增 runtime 事件。


**通过标准：** summary 包含 `samples`、`hit_count`、`hit_rate`、`natural_completion_count`、`avg_steps_used` 和 `reasons`；不保存任务正文。

### 步骤 16：检查动态安全阀策略

**操作：**

```powershell
.\.venv\Scripts\python.exe -m pytest agent\tests\test_runtime_budget.py agent\tests\test_pi_runtime.py -q
```

重点检查：软预算内允许继续；工具失败达到阈值、上下文压力过高或耗时达到阈值时停止；固定最大步数仍是硬上限。

**作用/目的：** 验证动态策略是确定性、可解释和可回退的，而不是取消安全阀或引入黑盒决策。

**通过标准：** 同一输入和事件序列得到同一预算决定；策略不会绕过最大步数、取消、超时和错误保护；默认配置 `dynamic_budget_enabled=False` 时，0.2.2 的默认行为不变。

## 6. 总体验收标准

以下条件必须全部满足，0.2.3 才算技术实现验收通过：

1. Python 全量测试通过：`278 passed, 1 skipped`。
2. ruff、`git diff --check`、扩展测试、TypeScript 检查和扩展编译均通过。
3. runtime 事件合同版本为 1，字段稳定、未知事件可忽略、敏感正文不外泄。
4. 时间线最多 80 条事件、单字段 160 字符、单行 320 字符、总量 12,000 字符。
5. 时间线异常或超限不影响正常回答、工具调用和最终状态。
6. 时间线保持调试型最小视图，不新增筛选、搜索、持久化和复杂可视化。
7. benchmark 能输出压缩前后 token、节省比例、压缩耗时、端到端延迟、失败率和人工质量评测状态。
8. 没有真实 paired 数据时，明确标记真实评测未完成，并保持 summarizer 不引入。
9. trace 维持 `keep-in-memory`，隐私字段、保留周期和容量上限有文档；不默认落盘。
10. 预算统计能区分自然结束和安全阀命中；动态策略保留硬上限并默认关闭。
11. 0.2.2 的压缩回退、历史 session 兼容、默认 native runtime、工具轨迹折叠和现有 UI 时序不回归。
